AuthorOpenEricLBuehler/mistral.rs

CPU-offloaded MoE decode: dequantize only the routed experts (#2558)#

Problem
On x86_64 the CPU indexed-MoE path dequantized the whole stacked [experts, n, k] tensor on every call, then gathered the few experts the router had picked. QTensor::indexed_gemv is aarch64-only in candle-core 0.11.1, so x86 always took that fallback.
Change
Slice only the routed experts out of the packed storage, run a quantized matmul per expert, and cache those per-expert matmuls on the layer (GgufMatMul) so candle's repacking is paid once. Layouts it does not handle fall back to the old path; aarch64 still tries indexed_gemv first. Stacked on #2556 (also mine, open), which lets CPU-offloaded experts run at all when activations are on CUDA.
Result
About 50x faster decode, measured on one setup: Qwen3-30B-A3B Q4_K_M, RTX 4090, experts for layers 30 to 39 on CPU, x86_64. Baseline is master plus #2556 (this PR is stacked on it): 0.26 tok/s (54 tokens). This PR: 13.2 tok/s on the same prompt.
Validation
New CPU-only tests compare the new path against the full-dequantize reference. Not tested: aarch64, other models, other GPUs. The cache keeps one repacked copy of each used expert; I estimate 3 to 4 GB extra RAM for ten offloaded layers of this model, but did not measure it. TODO: measured RAM

AuthorOpensgl-project/sglang · state-spaces/mamba

Packed prefill: one request's inf/NaN no longer corrupts co-batched requests (SGLang #51342, Mamba #1083)#

Problem
The Mamba SSD Triton kernels remove other sequences' contributions by multiplying them by a clean 0.0. Under IEEE 754, 0 × inf and 0 × NaN are still NaN. So one sequence's non-finite x or B leaked through tl.dot into every other sequence sharing the chunk, and into their cached SSM state, which stays wrong for every later decode step. In multi-tenant serving this is a request-isolation failure: one request's degenerate input can corrupt every request batched with it.
Change
SGLang: sanitize x and B on load in the chunk-state and chunk-scan kernels (v - v is 0 for finite values, NaN otherwise). The SGLang issue (#51108) was reported by another contributor; I submitted the fix PR (open). Then I traced the pattern to the upstream reference implementation, reproduced it (#1082) and submitted a fix there (open) across the chunk-state, chunk-scan (including prev_states) and state-passing kernels, sanitizing only chunks that straddle a sequence boundary. A lone sequence's own NaN still propagates instead of being hidden.
Validation
SGLang: the regression test fails on unpatched code (30 of 30 outputs non-finite, non-finite final state); the existing 371-case test_mamba_ssm_ssd.py suite passes; output is bit-identical on finite inputs; timing differences of −0.6% to −2.3% are within noise. Mamba: an 8-case matrix (same chunk or chunk boundary × x or B × inf or NaN) plus a lone-sequence test fails unpatched and passes patched. One remaining bf16-tolerance case in that file fails identically on unpatched code. vLLM's copy is not affected, because it splits chunks at sequence boundaries.
Status
Both PRs open, no maintainer review yet.

AuthorOpenggml-org/llama.cpp

CUDA out-of-memory in MMQ fails the request, not the process (#32440)#

Problem
When the CUDA VMM pool could not grow during mul_mat_q (cuMemCreate returns out of memory), the backend aborted the whole process, taking down a server with every in-flight request.
Change
The pool gets a try_alloc that returns null on OOM, and MMQ uses it for all its pool temporaries. The op returns without launching, graph_compute stops with GGML_STATUS_ALLOC_FAILED and drops the cached CUDA graphs so a partial capture is never replayed, and llama_decode returns −2 so the server fails only that request. The PR also stops the VMM destructor aborting when the first grow failed. Fixes #31974.
Validation
tests/test-backend-oom.cpp fails for MMQ on master and passes here. llama-bench on an RTX 3090 (14 alternating rounds, Qwen3-1.7B Q4_0 and Q4_K_M): all six 95% confidence intervals for the change include zero. Scope: MMQ only; the other ops still abort.

What is an H100 actually doing?#

Method
Measure peak bandwidth and FLOPs on the card instead of quoting the datasheet, predict each model's batch-1 decode rate from its measured weight bytes, then attribute the residual. Five models: Qwen3-0.6B, 8B and 14B, OLMoE-1B-7B, DeepSeek-V2-Lite. Little's Law held within 3% on every run as a consistency check.
Findings
Qwen3-8B reaches 81% of the measured bandwidth ceiling at batch 1. A small model is not a fast model: Qwen3-0.6B has the highest token rate and the worst utilization (28%), because it is overhead bound. A mixture of experts gets less efficient as batch grows (DeepSeek-V2-Lite goes from 6 of 64 experts touched at batch 1 to nearly all at batch 64). FP8 KV cache is neutral at low concurrency, 4 to 6% faster at high concurrency, and nearly doubles KV capacity (407,248 to 790,272 tokens).
Negative result
An earlier pass without cache controls produced a throughput knee, an FP8 regression and a prefix-caching effect, none of which exist: repeated runs against one server were hitting a warm prefix cache. I corrected the study and reported the methodology issue upstream (vllm#52884). Every number now comes from runs with the cache flushed, a fixed request count, and three repeats.
Limits
One serving stack, so hardware limits and vLLM limits are not separated. Clocks could not be locked, so figures are best-of-N (1.2% measured run-to-run spread). No kernel-level profiling: the launch-overhead figure bounds the cost without saying which kernels pay it. No prefill numbers reported, because those runs were contaminated by cache.

Uncle: a terminal-native coding agent with verifiable review#

What it does
Turns a GitHub issue into a planned, implemented, independently reviewed, tested pull request. Implementation and review run as separate processes, and "tests pass" comes from exit codes, not from any agent's opinion. It works with Claude, Codex, Kimi, self-hosted models and AWS Bedrock.
Evidence
Test, review and approval evidence is bound to the exact Git tree, recorded as in-toto/DSSE attestations with SSH or Sigstore signing and standalone verification (uncle verify), so an edit after review invalidates the review.
Deployment
Each task runs in an isolated Daytona sandbox, and results are published through the GitHub API so intermediate work stays off customer branches. It runs commercially as Anya Sharp on Seren: 176 paid customer tasks as of November 18, 2026. Machine learning research

Independent studies, each built on public or self-collected data with the full pipeline, tests, and negative results published. Statistical and causal-inference work, kept separate from the inference engineering above.

Are agent benchmark scores stable enough to trust?/deccan#

Tests whether agent benchmark comparisons survive perturbations that should not matter: prompt paraphrase, tool renaming, distractor tools, instance resampling, temperature, and task order, across 156 episodes on three procedurally generated task families. All six axes shifted scores, and detecting a 3-point gap between models turns out to require hundreds to thousands of instances. The conclusion is a cost estimate: a comparison you can defend costs one to two orders of magnitude more than these are usually given.

Read the study Code LLM agents · measurement · statistics

What is faster block propagation worth on Ethereum?/optimum#

A causal study of block propagation latency and validator revenue, built from 216,000 mainnet slots of public Xatu and MEV relay data. Identification comes from the protocol's 4-second attestation deadline (a sharp regression discontinuity: correct head votes fall from 95.9% to 67.4% across it), and the value of a faster transport is priced through three channels, with roughly 90% arriving via MEV timing rather than attestation rescue. Includes a 245-day analysis of the vendor's only real deployment, which finds no adoption-shaped change in propagation.
