What Agent Provenance Has to Do That CI Never Did

2026-11-10 · Brian Woods

Binding review evidence to the exact code that was reviewed is not a new idea. SLSA names the threat. GitHub ships a checkbox for it. Other people are already attaching in-toto attestations to agent-authored pull requests.

What is new is that coding agents break two assumptions those tools rely on: that the system producing the evidence is separate from the author, and that an approval from your account means you approved. This post covers what the existing tools do, where they stop when an agent is doing the work, and how to close the gap. I'll use Uncle, the open-source tool I'm building, as the worked example, but the mechanisms are the point. Any tool can implement them.

Why this matters now

Writing code used to be the expensive part, and the person who wrote it could vouch for it. Vibe coding ends both. Anyone can produce a working app in an afternoon, and the person shipping it often hasn't read most of the code. They can't vouch for it, so whatever trust there is has to come from the process that produced it.

The volume is already large. A study of public GitHub activity found 2,830,284 agent-authored pull requests between January 2024 and April 2026. AI review of those PRs grew by more than two orders of magnitude between early and mid 2025, and agents now routinely review other agents' code. The authors note that human review of these PRs can't be observed in their data. (Selvanayagam and Ghaleb, ESEM 2026)

That last point is the problem. When a downstream user, a reviewer, or you six months later looks at a change, nothing says whether a person approved it, which tree an agent reviewed, or whether the tests ever ran. These apps handle real user data, and today's vibe-coded app becomes tomorrow's dependency. The software supply chain spent a decade learning not to trust artifacts without provenance. Agents are making code without provenance the default again.

What already exists

If one of these covers your case, use it.

  • The SLSA threat model lists "modify code after review" as a named threat: a reviewer approves a good change, then the author swaps in bad code. The prescribed fix is to require review of the most recent revision before submission. (SLSA threats)
  • The SLSA Source Track defines attestations for source revisions, including whether code review happened. Its review requirement says trusted robots may be exempted from code review. (SLSA source requirements)
  • GitHub branch protection can dismiss stale approvals when new commits are pushed and require approval of the most recent reviewable push. Graphite's dismiss-stale-approvals action refines it by comparing range-diffs.
  • agentattest binds an AI coding-agent run to a git patch, tree, PR and approval state in an in-toto Statement, signed with Sigstore. Its README treats agent and model names as self-asserted metadata.
  • attested turns a test run into a signed in-toto receipt for agent-authored pull requests, signed in GitHub Actions.

These are good tools. The platform-side ones assume a person behind the account and a trusted CI system producing the evidence. Coding agents remove both.

The assumptions coding agents break

1. The evidence producer is separate from the author. In normal CI, the developer pushes code and a runner they don't control produces the test results. A coding agent runs on your laptop, in your repository, usually with a shell. It is the author and it shares a filesystem with wherever the evidence gets written. If the agent can write the file that says "tests passed," that file is a claim, not evidence.

2. An approval from your account means you approved. GitHub knows which account clicked approve. It cannot know whether you read the diff or whether an agent running under your gh token approved on your behalf. Agents act with their user's credentials, so "approved by Brian" stops meaning what it says.

3. The work happens before the platform sees it. An agent may run dozens of implement, review and fix loops locally before anything is pushed. Platform-side controls start when a pull request exists. Everything before that, including which tree the reviewer actually looked at, is invisible to them.

Agents also add a failure mode human developers rarely have: they report success for checks that never ran. The linter wasn't installed, the network was down, the test command timed out, and the summary still says "all checks pass."

What current tools don't do

Each row is a place where the existing assumption fails once an agent is doing the work.

Question Existing tools assume With a coding agent What's needed
Where is evidence produced? On a CI runner, after push Locally, before any PR exists Bind evidence to trees during local work
Who writes the evidence? A trusted CI system The agent shares the filesystem A driver writes it from exit codes it observed, and detects tampering
Who approved? The account holder An agent using your credentials Record human approval and delegated approval as different things
What if a check didn't run? The CI job fails The agent says "done" Record unavailable and treat it as blocking
Did the code change after review? Stale PR approvals get dismissed Changes before push are invisible Check that the reviewed, verified and published trees are identical
Who holds the signing key? CI's OIDC identity A key on the agent's machine A key the agent can't use

To be fair to agentattest: it records an approval state and fails on missing evidence. As far as I can tell from its README, it doesn't separate human from delegated approval or say how checks that never ran are represented. If I've got that wrong, I'd like to know.

How to do it

These are the mechanisms Uncle uses. Each one closes a row of the table above.

  1. Bind every stage's evidence to a Git tree. When a stage finishes (requirements, review, plan, implementation, verification, audit, release), write an envelope recording its result, the digests of its evidence documents, and the artifact digest. The artifact is the Git tree of the working files, minus the tool's own state. Serialize it as canonical JSON (RFC 8785) so hashes and signatures are reproducible.
  2. Let the driver write evidence, never the model. The orchestrating process writes envelopes from validator exit codes, gate records and its own hashing. The envelope directory is driver-owned: if anything writes to it during the implementation stage, the driver reverts it from a pre-stage snapshot, logs the attempt and stops the run.
  3. Make "didn't run" a result. Each stage records pass, fail or unavailable. Review and audit envelopes are pre-written as unavailable before the reviewer starts, so a reviewer that crashes or never returns leaves that on record. For review, verification and audit, fail and unavailable both block release, and no flag or environment variable changes that.
  4. Record who approved separately from who delegated. Each gate records approved_by (a person) separately from delegated_by (unattended, supervisor:explicit:<name>, supervisor:standing:<name>). Only a human keystroke satisfies a required gate. The verifier refuses a gate a supervisor agent approved and reports unattended gates as not human verified.
  5. Invalidate downstream evidence on change. Re-approving a document, or going back into implementation, deletes every envelope after it. Evidence can't outlive the inputs it was produced from.
  6. Check tree equality at the end. Before release, confirm that implementation, verification input and audit input all name the same tree. Then confirm the published tree equals that tree and the attestation subject. Wrap the result in an in-toto Statement with a DSSE envelope so anyone can verify it with standard formats. Uncle's verifier is a single Python file that needs only git.
  7. Sign with a key the agent can't use. Without a signature you get integrity, not authenticity: anything that can rewrite the code can rewrite an unsigned attestation. An ordinary SSH key loaded in ssh-agent doesn't help either, because an unsandboxed agent can call ssh-keygen -Y sign just as the driver does. Use a hardware key that requires a touch (an SSH sk- key) or Sigstore's interactive login, and supply a trust root at verify time.

None of these is cryptographically novel. The design work is in deciding what the agent is allowed to touch, and in making the absence of evidence count against a change.

What this still doesn't prove

  • Correctness. A verified change went through the process on the code you have. It can still be wrong or insecure. The review is only as good as the reviewer, and the tests only as good as the tests.
  • Safety from a hostile agent with your keys. If the agent can use your signing key, it can sign a forged attestation. Hardware keys and sandboxes are the defense, not the attestation format.
  • A compromised machine or verifier. If the driver or the verifier itself is compromised, every guarantee above is gone.
  • Uncle's own history, today. The attestations committed to Uncle's repository are unsigned, so verifying them gives integrity only (exit 3). Some changes were committed directly, without an attestation.

Open problems I haven't solved yet:

  • Concurrent merges. Two changes reviewed against the same parent produce a merged tree nobody reviewed. That needs an integration attestation that is explicit about what was re-verified and what wasn't.
  • History. Verifying the latest change should also tell you every earlier change passed. That means chaining attestations along the commit graph and logging their digests to a transparency log like Rekor, so a stolen key can't rewrite the past.

The short version

Provenance tools were built for a world where the build system was trusted and an approval came from a person. Coding agents run next to the evidence and approve with your credentials. The fix isn't new cryptography. It's a driver the agent can't overrule, evidence that records what didn't happen as well as what did, and approvals that say who actually made them.

Uncle is open source at github.com/unclehq/uncle. The artifact-integrity problem is covered in more depth in The Review Wasn't Wrong. It Was a Review of Different Code. If you know a tool that already does any of this, tell me. I'd rather cite it than reinvent it.
