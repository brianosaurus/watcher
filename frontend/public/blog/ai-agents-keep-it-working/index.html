AI Agents Can Build an Application. Can They Keep It Working?

2026-11-10

The hard part of agentic software development isn't generating code. It's making sure every new change preserves what already works.

We've reached a strange point in software engineering.

An AI coding agent can build an entire application. Give it a specification, access to a repository, and enough time, and it can produce thousands of lines of code, tests, documentation, and a working interface.

That's impressive. But building an application once isn't the same as developing one.

Real software is never finished. Requirements change. Bugs appear. Features accumulate. Dependencies evolve. A working application becomes the starting point for the next change, and then the next, and then the next.

That's where agentic coding gets interesting.

If we want AI agents to develop complete applications that improve over time, rather than repeatedly produce impressive but fragile prototypes, we need a way to establish what works, preserve that evidence, and verify every subsequent change against it.

Without that discipline, we're not really developing software. We're generating successive versions and hoping each one is better than the last.

The problem isn't the first build

Imagine asking an AI agent to build a web application.

It creates a backend, a database, an authentication system, and a frontend. It writes tests. Everything passes.

You review the result. It looks good.

Now you ask the agent to add a feature.

It changes twelve files, updates several dependencies, modifies the database schema, and adjusts some existing functionality to accommodate the new feature.

The new feature works.

But does everything else?

Maybe. The agent might have excellent tests. It might have reviewed its own changes. It might even have used a second agent to inspect the implementation.

None of those things, by themselves, establish that the application is better than it was before.

And none of them necessarily establish that the code being delivered is the exact code that was reviewed.

These are two separate problems.

The first is correctness: does the software behave as intended?

The second is integrity: is this the same software that was tested, reviewed, and approved?

You need both.

A passing review is evidence about a particular version of the code

Suppose an AI agent completes a change.

A second agent reviews it. The tests pass. The change is approved.

At that moment, we have evidence about a particular state of the repository.

Call it Tree A.

Now suppose the coding agent makes one more modification after the review. Perhaps it fixes a typo, updates the README, or changes a configuration file.

We now have Tree B.

The original review may have been perfectly accurate. The tests may have been perfectly valid.

But they were performed against Tree A.

We cannot automatically transfer that evidence to Tree B.

This is a fundamental problem with treating agentic development as a conversation rather than an engineering process.

An agent can say it finished. Another agent can say it reviewed the work. A third can summarize the results.

But what exactly did they review?

And is that what we're about to ship?

A one-line experiment

I built an open-source coding agent called Uncle to explore this problem.

One of its design principles is that verification evidence should be tied to the exact Git tree it describes.

Git already gives us a useful primitive for this. A tree object identifies the contents and structure of a repository snapshot. Change a tracked file, and the resulting tree identity changes.

That lets us perform a simple experiment.

Start with a repository that has completed Uncle's review and verification process.

Verification passes.

We have evidence associated with the reviewed Git tree.

Now change one line in README.md and commit it.

Nothing dramatic. No malicious code. No complicated exploit. Just a documentation change.

But the Git tree is now different.

Run verification again, this time asking whether the original review evidence applies to the new tree.

It shouldn't pass.

Not because the README change is necessarily wrong.

Not because the application is necessarily broken.

It should fail because the evidence describes a different artifact.

The original review hasn't become invalid. It remains valid evidence about the original tree. It simply cannot establish that the new tree received the same review.

To restore verification, the changed tree needs new evidence.

That's the entire idea.

A system should never claim that a version of software has been reviewed merely because a previous version was reviewed.

This experiment demonstrates an integrity property, not a guarantee of correctness. And it depends on the verifier explicitly comparing the new tree against the original attestation. Merely verifying the old artifact again should still succeed.

Why this matters more with AI agents

Human developers make mistakes. They forget to run tests, introduce regressions, and occasionally commit changes after review.

We've spent decades developing tools and practices to reduce those risks.

Version control. Continuous integration. Code review. Branch protection. Reproducible builds. Release signing.

AI agents don't eliminate the need for those practices.

They make them more important.

The reason is velocity.

A human engineer might make a handful of meaningful changes in an afternoon. An AI agent can modify dozens of files in minutes, and multiple agents can work on different parts of the same system simultaneously.

The cost of producing changes has collapsed.

The cost of understanding whether those changes are safe has not.

In fact, it may have increased.

When an agent can generate more code than a human can reasonably inspect, we need stronger ways to establish what was changed, what was tested, what was reviewed, and whether the resulting artifact is the one we intended to deliver.

We cannot solve that problem by asking the agent to be more careful.

We need engineering mechanisms that don't depend on the agent remembering to be careful.

Software development is a sequence of verified transitions

I think this changes how we should think about agentic development.

Instead of treating software development as a sequence of prompts, we should treat it as a sequence of transitions between known states.

Start with a verified application.

Call that state A.

Ask an agent to implement a feature. It produces state B.

Before accepting B, establish several things:

  • The intended feature works.
  • Existing required behavior still works.
  • The change satisfies the project's constraints.
  • The review and test evidence applies to the exact resulting artifact.
  • The artifact being accepted is the one that passed those checks.

Only then does B become the new accepted baseline.

The next feature starts from B and produces C.

Then C must earn its place as the new baseline.

A → B → C → D.

Each accepted state has evidence supporting it.

Each transition must satisfy the requirements for acceptance.

And every piece of evidence must be associated with the artifact it actually describes.

This doesn't mean every change needs a human to read every line of code. It means every accepted change needs to pass a defined verification process.

Some checks can be automated. Some can be performed by independent agents. Some require human judgment.

The important thing is that the process produces evidence rather than reassurance.

Verification is not the same as proving correctness

There's an important limitation here.

A Git-tree attestation cannot tell us whether a feature is useful.

It cannot prove that an algorithm is correct.

It cannot establish that a security vulnerability doesn't exist.

It cannot guarantee that the tests cover every important behavior.

What it can do is establish that particular evidence applies to a particular artifact.

That sounds modest, but it's essential.

Imagine running an excellent test suite against one version of an application and then deploying a different version.

The quality of the tests doesn't help if the results aren't tied to what you deploy.

The same is true of agent reviews.

We need both meaningful validation and artifact integrity.

Tests and reviews establish properties of software, within the limits of what they actually check.

Attestations and tree identity establish which software those results describe.

Neither replaces the other.

The application must improve, not merely change

There's another piece of this that I think deserves more attention.

Passing verification doesn't automatically mean an application has improved.

A new feature might work while making the product harder to use. A refactoring might preserve test results while making the system more difficult to maintain. A performance optimization might help one workload and hurt another.

So the acceptance process needs more than a green checkmark.

It needs explicit expectations.

What behavior are we trying to add?

What behavior must remain unchanged?

What performance, security, reliability, and compatibility constraints must continue to hold?

How will we know whether the change was successful?

These questions are familiar to experienced engineers. They're also exactly the questions that become easy to skip when generating software is nearly effortless.

The faster we can build, the more important it becomes to define what success means before we build.

For an agentically developed application, I would want each accepted version to carry enough evidence to answer two questions:

Is this the exact artifact we evaluated?

Did that evaluation establish the properties we require?

The first is an integrity question.

The second is an engineering question.

Together, they provide a foundation for continuous improvement.

They still don't guarantee that every accepted version is objectively better. That requires choosing good requirements, tests, and measurements. But they give us a disciplined way to make progress and detect regressions instead of relying on intuition.

The only sustainable way forward

I don't believe every AI coding project needs Uncle.

There are other ways to implement these ideas. GitHub branch protection, CI systems, artifact attestations, reproducible builds, and established software supply-chain frameworks already provide important pieces of the solution.

But I do believe that some form of evidence-backed, artifact-bound acceptance is necessary if we're going to rely on agents to develop and maintain substantial applications over time.

The specific tools are negotiable.

The engineering principle isn't.

If we cannot establish which version of the software was evaluated, what requirements it satisfied, and whether the version we're accepting is the same one, we have no reliable basis for claiming that our application is improving.

We can keep prompting agents.

We can keep generating features.

We can keep watching demonstrations that look fantastic.

But eventually we need to know whether the application we have today is actually better than the one we had yesterday.

And we need to know that without simply asking the agent that wrote it.

That's the problem I'm working on with Uncle.

AI agents have made building software dramatically easier.

Now we need to make accumulating trustworthy improvements just as systematic.

Because the future of agentic software development isn't an agent that can build an application once.

It's an engineering process that lets agents keep improving that application without losing what made it work in the first place.

Uncle is open source: github.com/unclehq/uncle. For a closer look at the artifact-integrity problem, see The Review Wasn't Wrong. It Was a Review of Different Code.
