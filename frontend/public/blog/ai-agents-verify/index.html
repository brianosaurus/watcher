AI Agents Can Write Code. Who Verifies Their Work?

2026-11-08

We are giving coding agents more autonomy without changing how we establish trust in the software they produce.

AI coding agents have crossed an important threshold. They can take an issue, explore a repository, write code, run tests, and open a pull request. They can build a working application from a sentence. Some can do it in minutes.

That's impressive. It's also created a problem I don't think we've adequately addressed.

We're allowing the same system that writes the code to tell us whether the code is good.

An agent implements a feature, runs some tests, reviews its own changes, and reports success. We get a summary that says the implementation is complete, the tests pass, and the code is ready.

But what actually happened?

Did the tests run? Did they finish successfully? Did the reviewer examine the final version of the code? Did the code change after review? Is the artifact we're about to merge the same artifact that passed verification?

Those are different questions from whether the agent believes it did a good job. And they're questions we should be able to answer without asking the agent.

The agent is not the authority

For most of my career, I've worked on systems where correctness matters more than the confidence of the component producing an answer. At Yahoo, I worked on anti-spam infrastructure handling billions of messages a month. More recently, I've worked on distributed systems, ML infrastructure, and LLM inference.

One lesson from that work has stayed with me: a component shouldn't get to declare its own output trustworthy just because it produced it.

We already understand this in traditional software engineering. The developer writes the code. Tests execute independently. CI records the results. Reviewers examine the changes. The repository maintains the history. Release systems decide what gets published.

These mechanisms aren't perfect. They don't guarantee correct software. But they establish boundaries between producing something and deciding whether to trust it. AI agents make those boundaries more important, not less.

A coding agent is capable of making mistakes, misunderstanding instructions, overlooking failures, and producing plausible explanations for things that didn't happen. That doesn't require malicious intent. A model can confidently report success because it misunderstood a tool response or lost track of an earlier failure.

The more autonomous the agent becomes, the less reasonable it is to treat its final summary as authoritative.

A second agent isn't enough

One popular response is to have another model review the first model's work. That's useful. I use independent review myself. But it doesn't solve the entire problem.

Suppose Agent A implements a change. Agent B reviews it and approves it. Agent A then modifies one file to address a separate issue before publishing. The final code is no longer the code Agent B reviewed.

Both agents might have behaved reasonably. The review might have been excellent. The tests might have passed. But the review no longer establishes anything about the final artifact. Here's a simplified example:

Implementation       tree f12b8...
                         |
                         v
Independent review   tree f12b8...   PASS
                         |
                         v
Verification         tree f12b8...   PASS
                         |
                         v
Publication          tree 91ae3...

                     NOT VERIFIED

The important distinction is that the review wasn't necessarily wrong. It was a review of different code.

Adding more reviewers doesn't fix this. Neither does using a more capable model. You need a way to establish that the thing being published is the thing that passed the required process.

The change is the unit of trust

Most agent frameworks are organized around the agent. Which model is running? What tools can it use? How much context does it have? How does it recover from failure? How do multiple agents coordinate? Those are important engineering questions.

But I've become more interested in a different question: what can we prove about the software change after the agents are finished?

A software change has an identity. In Git, we can identify the contents of a tree using its hash. That gives us something concrete to attach evidence to.

Instead of recording that an agent said it completed a review, we can record that a review stage completed against a particular tree. Instead of accepting a claim that tests passed, we can record the actual verification result. Instead of recording that a person approved something, we can bind the approval to the artifact they examined. And before publication, we can check whether the artifact still matches.

The intended process becomes:

Requirements
     |
     v
Approved plan
     |
     v
Implementation       tree f12b8...
     |
     v
Independent review   tree f12b8...   PASS
     |
     v
Verification         tree f12b8...   PASS
     |
     v
Human approval       tree f12b8...
     |
     v
Publication          tree f12b8...

                     VERIFIED

If the tree changes, the evidence no longer applies to the new tree. That sounds obvious. But it's a property that needs to be enforced by the workflow, not merely requested in a prompt.

The agent shouldn't write its own evidence

There's another subtle problem. Suppose an agent completes a task and writes a JSON file containing its results:

{
  "implementation": "pass",
  "review": "pass",
  "tests": "pass",
  "approved": true
}

That file is structured, but structure doesn't make it trustworthy. If the agent controls the evidence, it can accidentally or deliberately misrepresent the outcome.

A better approach is for the system coordinating the workflow to record what actually happened. The verification driver invokes the checks, observes their exit codes, records the artifact identity, and produces the evidence. The agent can generate code and explain its decisions. It cannot turn a failed test into a passing result by writing a convincing summary.

The evidence also needs to distinguish between three outcomes:

pass
fail
unavailable

That third state matters. A test that never ran isn't a passing test. A reviewer that timed out didn't approve the change. Missing evidence is not evidence of success. A workflow can have policies about what to do when evidence is unavailable, but it shouldn't rewrite history to make the result look better.

I built Uncle to explore this

I've been working on an open-source project called Uncle. Uncle is a terminal-native development system that orchestrates coding agents such as Claude, Codex, Kimi, and locally hosted models. You can describe an application or give it a GitHub issue. It plans the work, implements it, performs independent review and verification, and prepares a pull request. You can talk to Uncle while it works, redirect an implementation, ask questions, or let it run unattended.

The part I'm most interested in, though, isn't generating the code. It's establishing what happened afterward.

Uncle separates the coding agents from the workflow driver that records verification evidence. The implementing agent doesn't approve its own work. Reviews and checks are associated with the relevant Git tree. Human approvals are recorded separately from delegated decisions.

For completed changes, Uncle can produce a portable attestation using an in-toto statement wrapped in a DSSE envelope. The attestation binds together the requirements, plan, implementation artifact, review evidence, verification results, approvals, and publication artifact. The goal is to let someone independently check whether the published change went through the process claimed for it. For example:

uncle verify

Or for a pull request:

uncle verify 123

If the Git tree no longer matches the artifact identified in the evidence, the verifier refuses to call it verified. The verifier also distinguishes artifact integrity from signature authenticity. An unsigned record or a signature without an established trust root is not equivalent to trusted, authenticated provenance.

These distinctions are deliberate. I don't want a system that says "verified" merely because that sounds reassuring. I want one that can explain what it checked, what passed, what failed, and what it couldn't establish.

Verification is not correctness

This is an important limitation. A change can pass every required stage and still contain bugs. A reviewer can miss something. Tests can be incomplete. A specification can be wrong. Two models can make the same mistake.

A valid attestation doesn't establish that the software is secure, correct, or useful. It establishes something narrower: that the evidence applies to the identified artifact and that the recorded process satisfies the verifier's requirements.

That's still valuable. If a test passed against one tree but we're publishing another, we should know. If a change was built unattended without human approval, we shouldn't describe it as human-approved. If the attestation isn't signed by a trusted identity, we shouldn't imply that it is.

These are not solutions to every problem in AI-generated software. They're basic engineering properties that should remain true regardless of how capable the models become.

Why this matters more as agents improve

Today, many coding agents still require substantial supervision. But the direction is clear. They're becoming more capable, more autonomous, and able to work on larger changes. As that happens, the amount of code produced by agents can grow much faster than our capacity to inspect it manually.

We can respond by adding more AI reviewers. We probably will. But those reviewers will also be probabilistic systems. They'll have their own failure modes, context limitations, and blind spots. I think we need two complementary approaches.

First, use models to do the work they're good at: implementing changes, finding defects, explaining code, and proposing repairs.

Second, use deterministic mechanisms wherever possible to establish facts that shouldn't depend on a model's judgment. Did a command execute? What was its exit status? Which artifact was reviewed? Which tree was published? Was approval given by a person, or delegated to an agent? Does the evidence still match? These are questions software can answer without an LLM.

The distinction matters because model intelligence and workflow integrity are not the same thing. A better model might write better code. It doesn't eliminate the need to establish what was reviewed, tested, and published.

What still needs work

Uncle is a developing open-source project, not a finished solution to software supply-chain security. Its integrity model has limitations. Not every change currently carries a signed attestation, and unattended changes are deliberately distinguished from human-approved ones.

The implementation also needs scrutiny. Are the trust boundaries correctly enforced? Are there edge cases where evidence can become stale? Are the verifier's assumptions appropriate? Can an agent influence something that should be outside its authority? Those are the kinds of questions I want other engineers to ask.

The project is written largely in Bash and Python, and it supports multiple coding-agent runners. There are opportunities to contribute to verification, tests, integrations, the terminal interface, and developer experience. I'm particularly interested in people who can find ways to break the integrity guarantees. A convincing counterexample is more useful than a compliment.

Delegate the work, not the responsibility

I don't think the future of software development is humans manually reviewing every line an AI agent writes. But I also don't think the answer is to trust an agent because it sounds confident, or because another agent agrees with it.

We need systems where agents can do increasingly substantial work while the boundaries around verification, approval, and publication remain explicit. That means separating what an agent can do from what it can declare authoritative. It means treating the software change as the object we're verifying. And it means preserving enough evidence that another engineer can independently evaluate what happened.

AI agents are getting very good at writing software. Now we need to get equally serious about proving what they actually did.

Uncle is open source and looking for contributors. The repository is at github.com/unclehq/uncle. If you're interested in coding agents, verification, developer tooling, or software supply-chain integrity, I'd welcome contributions, criticism, and attempts to break its assumptions.
